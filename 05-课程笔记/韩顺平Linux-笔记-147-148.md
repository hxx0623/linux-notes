# 一、147：权限操作思考题（课件 26.8）

## 1.1 题面

用户 `tom` 对一个目录有不同权限，目录里 `/home/test/hello.java` 是**只读文件**（`444`），问 tom 对它：

| 案例 | tom 对**目录**的权限 |
| --- | --- |
| 1 | `rwx` |
| 2 | `rw-`（**没有 x**） |
| 3 | `--x` |
| 4 | `-wx` |

> **关键前提**：`/home/test` 的属主是 `root`，tom 不是属主、不在 root 组 → **tom 落在 `other` 那一组**。所以设权限时看**最后一位**。

## 1.2 必须刻进脑子的机制表

| 你想干什么 | **实际依赖什么** | 为什么 |
| --- | --- | --- |
| **读文件内容**（`cat`） | 目录 **`x`** + 文件 **`r`** | `x`＝能穿过去定位到文件；`r`＝能读内容 |
| **改文件内容**（`>>`） | 目录 **`x`** + 文件 **`w`** | 同上 + 写权限 |
| **删文件**（`rm`） | 目录 **`w`** + 目录 **`x`** | ⭐ **文件本身权限完全不起作用** |
| **列出名字**（`ls`） | 目录 **`r`** + 目录 **`x`** | `r` 只给"名字清单" |

### 三个反直觉结论

1. **删文件不看文件权限** —— 文件名只是目录里的一条记录，删它 = 删目录项。文件是 `444 root` 也只读，照样删得掉。
2. **目录的 `r` 和"读文件"毫无关系** —— `r` 只管"能不能看到名字列表"。
3. **目录的 `x` 才是通行证** —— 没有 `x`，有 `r` 有 `w` 也进不去；**只有 `x` 没有 `r`，不能 `ls`，但知道文件名照样能 `cat`**。

> 仓库比喻：**`x`** = 大门钥匙（能进门）｜**`r`** = 货物清单（知道有哪些箱子）｜没清单但知道箱号，照样搬得走；没大门钥匙，有清单也进不去。

## 1.3 ⭐ 12 个答案 + 实测证据

| 目录权限 | 读 | 改 | 删 | 实测 |
| --- | --- | --- | --- | --- |
| `rwx`（777） | ✅ **ok** | ❌ no | ✅ **ok** | 读实测成功；删由案例 4 代证（机制相同） |
| `rw-`（776，无 x） | ❌ no | ❌ no | ❌ no | 三条全挡 |
| `--x`（771） | ✅ **ok** | ❌ no | ❌ no | `ls` 失败但 `cat` 成功 |
| `-wx`（773） | ✅ ok | ❌ no | ✅ **ok** | `rm -f` 后 `ls` 报"没有那个文件" |

**与课件给的答案完全一致（12/12）** —— 学习者是先自己推理（全对），再做实验验证的。

### 实测片段（案例 3，最精彩）

```bash
sudo chmod 771 /home/test          # drwxrwx--x
sudo -u tom ls  /home/test         # ls: 无法打开目录 '/home/test': 权限不够   退出码=2
sudo -u tom cat /home/test/hello.java   # hello java                            退出码=0
sudo -u tom bash -c 'echo x >> …'  # 权限不够                                  退出码=1
sudo -u tom rm -f …hello.java      # rm: 无法删除: 权限不够                     退出码=1
```

**同一个目录、同一个用户、隔了一行：一个失败一个成功。** 这就是"`r` 和 `x` 是两件事"的铁证。

### 案例 4 的证据（证明"删不看文件权限"）

```bash
sudo chmod 773 /home/test
sudo -u tom rm -f /home/test/hello.java     # 退出码=0
sudo ls -l /home/test/hello.java            # 没有那个文件或目录  ← 真删了
```

文件是 `root` 的、`444` 只读，**tom 照样删掉了**。

## 1.4 踩坑：`rm` 的"退出码 0"什么都证明不了

次次做案例 1 时没加 `-f`：

```
rm: 是否删除有写保护的普通文件 '/home/test/hello.java'?
③ 删 退出码=0
```

**GNU `rm` 的询问只认 `y`/`yes`**。直接回车 = 空回答 = **不是肯定 = 不删**，而且**退出码仍然是 0**（"没出错，只是依你的意思跳过了"）。

```
按了回车     → 文件还在，退出码 0
输入 y 再回车 → 文件没了，退出码 0
```

| 教训 | 说明 |
| --- | --- |
| 验证删除**必须 `rm -f`** | 否则 `rm` 自己的确认会挡住，看不到内核的真实裁决 |
| 验证删除**必须看删后 `ls`** | 退出码不可信，**文件真没了才算** |

> ⚠️ 这个坑在 **146 集粘滞位实验**里犯过一次，147 又犯一次 —— **同一类错误重复出现，说明"经验"还没变成"条件反射"。**

## 1.5 顺便：`ls` 的退出码是 2，其他是 1

| 退出码 | 含义 |
| --- | --- |
| `1` | 小问题（多个文件里有一个读不了，其余照做） |
| `2` | **严重错误**（连目录都打不开） |

**不同程序的退出码约定不一样**（`grep` 的 2、`rm` 的 1）。脚本里判断成败只用 `if cmd; then`，**别硬编码 `$? == 1`**。

## 2.2 启动流程（8 步，比 126 集更细）

```
① 固件自检 POST → 选启动设备
② 引导第一阶段
   ├─ BIOS+MBR：前 446 字节 boot.img → 接着扇区里的 core.img
   └─ EFI：ESP 里的 \EFI\centos\shimx64.efi → grubx64.efi     （128 集亲手做过）
③ 引导第二阶段：GRUB2 读 /boot/grub2/grub.cfg → 决定内核与参数
④ 加载 /boot/vmlinuz-*（内核）+ /boot/initramfs-*.img（临时根）
⑤ 内核解压自己 → 跑 initramfs → 加载挂载根分区所需驱动 → switch_root 到真根
⑥ 内核启动第一个用户态进程 /usr/lib/systemd/systemd    ← ⭐ PID 1
⑦ systemd 按 default.target **并行**拉起一批 unit
⑧ 到达 multi-user.target（文本）或 graphical.target（图形）
```

> CentOS 7 里 `/sbin/init` 是**指向 systemd 的软链** —— 老命令还能跑，干活的已是 systemd。

## 2.3 ⭐ 面试核心：CentOS 6 vs 7 对照表

| 维度 | **CentOS 6** | **CentOS 7** |
| --- | --- | --- |
| 初始化系统 | SysV init | **systemd** |
| 启动方式 | 🔴 **串行**脚本 | 🟢 **并行** unit |
| 配置文件 | `/etc/inittab` | unit 文件 |
| 运行级别 | `runlevel 0–6` | **target** |
| 默认目标 | `id:3:initdefault:` | `systemctl set-default` |
| 服务脚本 | `/etc/init.d/xxx` | systemd unit |
| 启停 | `service xxx start` | `systemctl start xxx` |
| 开机自启 | `chkconfig xxx on` | `systemctl enable xxx` |
| 查自启 | `chkconfig --list xxx` | `systemctl is-enabled xxx` |
| **依赖关系** | 脚本书头写数字（`# chkconfig: 2345 20 80`） | **声明式** `After=`/`Requires=`/`Wants=` |
| 日志 | 各服务自己写 `/var/log` | **journald 统一**（`journalctl`） |
| 速度 | 慢（串行+shell） | 快（并行+按需） |

### 面试话术（可直接用）

> "CentOS 6 用 SysV init，靠 `/etc/inittab` 定运行级别，然后串行执行 `/etc/init.d` 里的脚本，服务依赖得在脚本头写数字表示顺序。
> CentOS 7 换成 systemd，用 target 替代运行级别，unit 里用 `After=`/`Requires=` 声明依赖，能并行的并行，日志统一进 journald。
> **本质区别是：从「一串按顺序执行的脚本」，变成「一组声明了依赖、由调度器并行拉起的工作单元」。**"

## 2.4 26.10 七个命令 + Ubuntu 对照

课件原文（txt 抽取把空格弄乱了）：

```
netstat   //网络状态监控

find
ps -aux   //查看运行进程
```

| 课件命令 | Ubuntu 上 |
| --- | --- |
| `netstat` | 需装 `net-tools`，**推荐 `ss`** |
| `ps -aux` | ⚠️ 应为 `ps aux` 或 `ps -ef` |
| **`chkconfig`** | 🔴 **不存在** → `systemctl is-enabled` / `list-unit-files` |

### 更高级的答法：按"排障场景"组织

| 场景 | 命令 | 一句话 |
| --- | --- | --- |
| 进程卡住 | `ps aux` / `top` | 快照 vs 实时；`D` = 等 IO |
| 端口被占 | `ss -tlnp` | `-t`TCP `-l`监听 `-p`进程 |
| 磁盘满 | `df -h` → `du -sh *` | 先看分区再逐层找；都对不上 → `lsof +L1` 找"已删但仍被占用"的文件 |
| 盘和分区 | `lsblk -f` | 分区+文件系统+UUID+挂载点一次看全 |
| 整体负载 | `top` / `uptime` | load ÷ 核数 |
| 服务状态 | `systemctl status/enable/is-active` | 在跑 / 自启 |
| 找文件 | `find` / `locate` | 实时搜 vs 预建索引 |
| 翻日志 | `journalctl -u 服务 -b` | 本次启动该服务的日志 |

## 2.5 实测：系统里的启动链证据

```bash
systemctl get-default                     # graphical.target（桌面版）
ps -p 1 -o pid,comm=                      # 1 systemd
systemctl list-units --type=target --state=active   # 26 个 target
```

**26 个 target 的名字里就藏着层次**：

```
sysinit.target → local-fs.target → basic.target
              → nss-lookup.target → network.target
              → multi-user.target → graphical.target
```

| 名字模式 | 含义 |
| --- | --- |
| `*-pre.target` | 在 X 之前跑的准备工作（`local-fs-pre`、`network-pre`、`getty-pre`） |
| `*-setup.target` | 安全/完整性检查（`cryptsetup` 加密盘、`integritysetup`、`veritysetup`） |

**`journalctl -b` 的第一条就是启动流程的现场录像**：

```
kernel: Linux version 7.0.0-42-generic (buildd@lcy02-amd64-051) …
kernel: Command line: BOOT_IMAGE=/boot/vmlinuz-7.0.0-42-generic root=UUID=91f76578-… ro quiet splash
kernel: BIOS-provided physical RAM map:
kernel: BIOS-e820: [mem 0x0-…] ACPI NVS
```

| 日志 | 对应哪一步 |
| --- | --- |
| `Linux version …` | ④ 内核启动（连"在哪台机器编译"都有） |
| `Command line: … root=UUID=…` | ③ GRUB 传给内核的参数（与 `cat /proc/cmdline` 同源） |
| `BIOS-provided physical RAM map` | ① 固件把内存布局交给内核 |

> 🔑 **日志从内核第一句话就在记** —— 机器起不来时 `journalctl -b -1` 能看死在哪一步。

## 2.6 ⭐⭐ `systemd-analyze`：从"知道流程"到"能测量"

```bash
systemd-analyze
# Startup finished in 3.979s (kernel) + 7.381s (userspace) = 11.361s
# graphical.target reached after 7.365s in userspace.

systemd-analyze blame --no-pager | head -10
# 3.357s plymouth-quit-wait.service
# 1.941s fwupd.service
# 1.725s apt-daily-upgrade.service
# 1.276s logrotate.service
# 1.129s snap.seeded.service
# 1.103s snap.apparmor.service
# 1.076s snap.service
#  840ms NetworkManager.service
#  804ms gpu-manager.service
#  695ms dev-loop12.device

systemd-analyze critical-chain --no-pager
# graphical.target @7.365s
# └─multi-user.target @7.365s
#   └─plymouth-quit-wait.service @4.007s +3.357s
#     └─systemd-user-sessions.service @3.994s +8ms
#       └─network.target @3.977s
#         └─NetworkManager.service @3.137s +840ms
#           └─dbus.service @2.747s +206ms
#             └─basic.target @2.742s
#               …
```

### 为什么只显示 kernel + userspace 两段？

> **`firmware` 和 `loader` 那两段，是引导程序主动写进 EFI 变量告诉 systemd 的。GRUB 不写**（systemd-boot 才写）。拿不到就只能从内核启动开始算。

### ⭐⭐ 核心洞察：优化该优化谁

| 服务 | blame 排名 | 在关键链上？ | 优化效果 |
| --- | --- | --- | --- |
| `plymouth-quit-wait` 3.357s | 第 1 | ✅ **在** | **省 3.3 秒**（7.4s → ~4s） |
| `fwupd` 1.941s | 第 2 | ❌ 不在 | **省 0 秒**（并行跑，删了也不影响总时长） |
| `apt-daily-upgrade` 1.725s | 第 3 | ❌ 不在 | 省 0 秒 |

> **`blame` 告诉你"谁最慢"，`critical-chain` 才告诉你"谁最值得动"。**
> **总启动时间 = 关键链上所有 `+` 之和**，不是所有服务的总和。
>
> **面试加分句**："我优化启动不看 `blame` 排名第一，我看 `critical-chain` —— 并行的服务慢不拖总时间，串行链上的才拖。"

### `@` 和 `+` 别搞混

- **`@`** = 变成 active 的**时刻**（从开机算）
- **`+`** = 自己启动**花了多久**

**别拿 `@` 算加法** —— 有些 `@` 看着是乱的（某 mount 显示 `@4.933s` 却挂在 `@1.421s` 的 `local-fs.target` 下），那是 `critical-chain` 的显示特性，**只看 `+`**。

## 2.7 踩坑与纠正

| # | 坑 | 教训 |
| --- | --- | --- |
| 1 | `-o pid,comm=` 表头还在（`PID` 仍显示） | 等号只作用在紧跟的字段；要全去掉写 `-o pid=,comm=` |
| 2 | 我预测"`multi-user.target` 依赖里能看到 `basic.target`"，实测**没看到** | `list-dependencies` **默认只显示 `Requires=`/`Wants=` 这类依赖，不显示 `After=`/`Before=` 这类顺序**。要看全加 `--all` |
| 3 | 以为 `critical-chain` 的 `@` 时间能顺着算 | 不能，只看 `+` |

7. 为什么 `systemd-analyze` 有时只显示 kernel + userspace 两段？
8. `blame` 第一名就一定是优化重点吗？该看哪个命令？
9. `journalctl -b` 能证明启动流程的哪几步？
10. 验证"能不能删文件"时，为什么必须用 `rm -f` 并再看一次 `ls`？

<details>
<summary>答案</summary>

1. **都不能**。没有 `x` 就进不去目录，读和删的第一步就失败（有 `r` 有 `w` 也没用）。删还额外要求目录 `w`。
2. **文件本身不需要任何权限**（哪怕 `444` 只读）。需要**目录的 `w` + `x`** —— 删的是目录项。
3. `ls` **失败**（没有 `r`，看不到名字列表）；`cat 已知文件名` **成功**（有 `x` 能定位 + 文件有 `r`）。
4. CentOS 6 是**串行**执行启动脚本；CentOS 7 的 systemd 按声明的依赖**并行**拉起 unit。
5. `/sbin/init` 是**指向 systemd 的符号链接** —— 老命令兼容，实际干活的已是 systemd。
6. `chkconfig` → `systemctl is-enabled` / `list-unit-files --type=service`；`netstat` → `ss`。
7. 因为 `firmware`/`loader` 时间要靠**引导程序写 EFI 变量**告诉 systemd，**GRUB 不写**（systemd-boot 才写）。
8. **不一定**。要看 `systemd-analyze critical-chain` —— 只有关键链上的服务才影响总时长。
9. ① POST（`BIOS-provided physical RAM map`）、③ GRUB 参数（`Command line:`）、④ 内核启动（`Linux version`）。
10. 因为 `rm` 遇到写保护文件会弹确认，**回车不算确认、不删，但退出码仍是 0**。所以必须 `-f` 跳过确认，并用 `ls` 确认文件真的消失。
